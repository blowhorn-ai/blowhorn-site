blowhorn chrome active-tab

Ask the Chrome extension for the front tab's address and title, through the bridge, and print it. The popover's New order asks here first: it retries briefly and never uses Apple Events, so macOS never prompts for Chrome. If the live read has no tab, a reachable extension may return its last remembered normal-window HTTP(S) tab with stale and age fields. This command navigates nowhere, probes no tab's page, and contacts no platform: it reads only the front tab's own address and title, from the Chrome profile whose bridge answers first. No reachable extension or no live or remembered tab answers with no tab, and --json carries connected and a detail saying why. That read writes nothing but the bridge lock, the same lock chrome extension-status writes. --json emits the answer as one object, for a script or the desktop app.

blowhorn chrome attach-chrome

Start or report a dedicated Chrome that is open to remote debugging with no Allow dialog, so --chrome-launch cdp can attach to a real Chrome unattended. Chrome 136 and later ignore --remote-debugging-port on the default data directory, which is why this is a second Chrome on a tree of its own (~/.blowhorn/attach-chrome, on a port Chrome picks and records, bound to 127.0.0.1) and never your daily one. That port has no password and asks for no Allow, and loopback is shared by every macOS user on this Mac, so any other user signed in here can control that Chrome, its cookies and signed-in sessions included. That is why it is off by default: start and install-agent refuse without --allow-other-users. Sign it in only to the accounts Blowhorn posts from.

status (the default) reads that tree's Local State, DevToolsActivePort and SingletonLock and nothing else -- no browser opens, nothing connects -- and its last line says what to do next. signin opens the tree with no remote debugging at all, for the one-time sign-in to each account Blowhorn posts from, because some sites (Google among them) refuse to sign in inside a browser started with debugging on; quit that Chrome when you are done and the sign-ins carry over. stop quits the Chrome holding the tree the way Cmd-Q does (DevTools Browser.close, so fresh sign-ins are saved), waits, then sends SIGTERM; it signals only that Chrome and never SIGKILLs. install-agent adds a per-user LaunchAgent (ai.blowhorn.attach-chrome) that runs start once at each login, so scheduler ticks find it up, and uninstall-agent removes it (the Chrome keeps running). start launches Chrome on the tree, detached, with the port open, and prints the steps that finish the setup: point chrome.data_dir at the tree, map your profiles, then run with --chrome-launch cdp. It writes no configuration of its own. The tree is fixed and Chrome picks the port, so its one option of its own is the opt-in. A recorded port is evidence a Chrome is up on that tree, not proof a connect would succeed, and it counts only while a live Chrome holds the tree. Starting is refused when the tree is Google Chrome's own default data directory (never the one chrome.data_dir names, which step 1 above points at this tree), when a live Chrome already has a port recorded there, and while the tree is open without debugging (the signin window): quit that Chrome first. A port file a crashed Chrome left behind is cleared, not refused. --dry-run prints the command line and starts nothing.

blowhorn chrome confirm

Apply the confirm screen's confirmed choices: turn Chrome profiles into Blowhorn profiles, attach the discovered platform accounts, and map each Chrome profile -- the one write onboarding makes, and the person's confirm is the consent it records. The choices arrive as one JSON document on stdin (--payload-stdin), so a GitHub token or a Bluesky app password in it reaches neither argv nor the daily log:

{"assignments": [{"directory": "Profile 3", "profile": "ada-example", "create": true, "userId": "<the member's uuid, as org members lists them; omit it for a brand>", "platforms": {"linkedin": {"attach": true, "session": true}, "x": {"attach": true}, "github": {"attach": true, "token": "..."}, "bluesky": {"attach": true, "app_password": "..."}, "slack": {"attach": true}}}]}

Per assignment, in order: the Blowhorn profile (an existing one the payload names by profileId or by profile, the one the directory is already mapped to, or, with "create": true, a new one created in your Blowhorn account representing the member userId names, or nobody for a brand; a name the payload omits is proposed from the Google name, and a profile the organization does not have is never created without "create"); then the attached platforms' credentials, stored in your Blowhorn account and nowhere on this computer; then the mapping, exactly as chrome map records it and, when the extension is already on in that Chrome profile, paired the same way, opening the extension's pairing page there, since a run refuses a mapping the extension cannot prove; a profile without the extension on yet is paired once it is (the desktop's setup does this, or chrome map); then each attached platform's username as the profile's account there: a connection registered and linked to the profile, named for the username and pointing at its account page when the username is a handle, which is where the profile's handles are read from. A platform row the payload marks with "session": true (LinkedIn, Hacker News) stores a confirmed-session credential naming this Chrome profile directory instead of a password: it satisfies eligibility the way a session-capture platform's identity key does, because the run checks that Chrome session before it reaches for a password. GitHub stores GH_USERNAME and still waits for GH_TOKEN; Bluesky stores the handle and still waits for the app password; both may ride in the same payload. Slack stores nothing: its session is captured afterwards by 'profile auth --platform slack', and the result says so.

A profile the document marks with "in_use": false is recorded not in use: this computer's mapping for that directory is removed, the Blowhorn profile is added to defaults.exclude when that name is not already there, and the profile and its credentials are kept. A platform row with "attach": false is recorded not in use for that profile in .blowhorn.chrome-not-in-use.json beside the config file; a platform left out of the assignment is left as it was recorded. The credential is kept, and a later run on this computer skips a platform still recorded not in use. Marking a platform in use clears that skip for the Blowhorn profile on every Chrome directory in the record, so a later choice in the same document wins. Marking the profile in use again removes it from defaults.exclude only when this screen added that name; a name already in the list is left as written, spelling and notes included. Omitting "in_use" applies only the attached rows, as before.

Each assignment answers for itself in the result -- profile, whether it was created, the keys written per platform, the mapping, the accounts recorded, or the one-sentence refusal -- so a partial confirm is a successful confirm: what landed stays landed, and what refused says why, by name. The exit code is 0 when at least one assignment landed and 1 when none did; a store that cannot be reached is the named cause and exit 3. With --dry-run every check runs and nothing is written, created or mapped.

blowhorn chrome create-profile

Give Blowhorn a Google Chrome profile of its own, for a Chrome that has only its main profile. Asks Chrome to open a new window in a Blowhorn profile directory. With no --profile-directory it opens the first unused one in Local State: Blowhorn, else Blowhorn 2, Blowhorn 3, and so on, so adding another identity never touches a profile of yours. Chrome creates that profile the first time and opens it again every time after, so running this twice makes no second one. Chrome gives the new profile a default name such as Person 1, which Blowhorn shows as Blowhorn's profile. After the window opens, Local State is read back until a short bounded wait runs out, so the answer says whether Chrome listed the profile (confirmed): a missing directory after the wait is a named failure, not a silent spinner. With --sign-in, the window opens on that platform's sign-in page instead of a new tab, so the setup wizard can guide the single sign-in in that window, one platform at a time, without a mapping. Sign in there to LinkedIn, X and the other sites Blowhorn should use, then blowhorn chrome discover finds the profile and its accounts. Reads Local State only, before the open and after it to confirm; writes nothing, maps nothing, and drives nothing in the window. If no Chrome is running, Chrome starts to open the window and is left running. Your own profiles, windows and tabs are left as they are.

blowhorn chrome discover

Report, for every Chrome profile, the platform accounts discovery can see there -- the read behind onboarding's confirm screen. For each profile: its directory, display name and signed-in Google account (from Local State, as chrome profiles reads them), the Blowhorn profile it is mapped to, the platform rows discovery found, a proposed Blowhorn profile slug, whether that slug is free, and how the Google email resolves against the organization's Blowhorn users.

A platform row is a saved-login username and whether a session is live. The usernames come from the profile's Login Data and Login Data For Account, for an allowlist of hosts only (linkedin.com, x.com and twitter.com, reddit.com, news.ycombinator.com, github.com, bsky.app and bsky.social, slack.com): only the realm and the username are ever selected -- the password column is a blob Chrome encrypts, and it is never selected, decrypted or copied. Whether a session is live comes from cookie names in Cookies or Network/Cookies: presence only, never a value, except GitHub's dotcom_user, whose value is the login name itself and so is the GitHub username when a session is live. Hacker News's user cookie is not read at all: its value bundles the username with a session secret. History and LevelDB are never opened -- a visit is not an identity. No browser opens, and a file Chrome holds locked reads as 'not found', never as an error. Nothing is written to Chrome. For each Chrome profile mapped here and in use, whose identity holds, a LinkedIn, X or Reddit sign-in it is picked for is recorded as that profile's account in your Blowhorn account, and a sign-in that ended marks the account disconnected; nothing is deleted, and --local and --dry-run record nothing. A not-in-use row for a directory Chrome no longer has is dropped from the record beside the config file.

The resolution answers the create rule without creating: one (the email names exactly one Blowhorn user in the organization; that user's Cloud social links ride along, shown on the confirm screen but never treated as permission to post), several (the member candidates, for a picker), none (no member holds the email), or no-email (nobody is signed in to that Chrome profile). --json emits the whole survey with a stable shape, for the desktop app. A store that cannot be reached is the named cause and exit 3; an unreadable profile list is one sentence and exit 1.

--local reads Chrome's files only and never opens the store, so it works before sign-in: every row's mapping is null, its resolution is unresolved (or no-email) and its slug state unchecked. The desktop app runs it when it first opens, then merges the full survey once you are signed in. Chrome's Guest and System profiles are never listed.

blowhorn chrome extension-install

Write the native-messaging host manifest Chrome launches for the Blowhorn Chrome extension, and print where the unpacked extension lives so you can load it. The manifest is com.blowhorn.chrome_extension.json under Chrome's NativeMessagingHosts directory (~/Library/Application Support/Google/Chrome/NativeMessagingHosts on macOS, /.config/google-chrome/NativeMessagingHosts on Linux), named com.blowhorn.chrome_extension, type stdio, path an executable launcher chrome_extension-host in Blowhorn's directory (/Library/Application Support/Blowhorn on macOS, ~/.local/share/blowhorn on Linux) that runs the Python native-host program by default, or the Rust host with --native-host rust, and allowed_origins naming the extension id from the key in extension/manifest.json, the Chrome Web Store id and the older unpacked id. If you already installed the host, run this command again and reload the extension once. A missing key or an unreadable extension manifest is one sentence and nothing is written; --dry-run prints both paths and the manifest and writes nothing. This command does not launch Chrome and does not load the extension.

--profile <name> names the Blowhorn profile whose mapped Chrome profile should get the extension (resolved through blowhorn chrome map on this machine); --chrome-profile <directory> names the Chrome profile directory itself, as blowhorn chrome profiles prints it, and can be given more than once. --pace string Accepted by blowhorn chrome unmap because --pace is a global flag, but this command does no paced work -- it sleeps between nothing -- so the value changes nothing about how it runs and appears only in the Pace column of the -v summary. Resolved as CLI flag, then BLOWHORN_PACE, then defaults.pace in .blowhorn.yaml (normal when none is set); an unrecognized value is rejected before anything runs
--risk-profile string Accepted by blowhorn chrome unmap because --risk-profile is a global flag, but this command does no gated work -- no Risk Profile hold, cap or pace applies to it -- so the value changes nothing about how it runs. A value after the command word wins over one before it; an unrecognized value is rejected before anything runs

Also takes the shared flags: --config, --log-dir, --profile, --exclude, --headless, --chrome-launch, --headed, --dry-run, --verbose.
